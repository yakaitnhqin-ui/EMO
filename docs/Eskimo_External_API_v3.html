Section 0

Partnership Models

Eskimo offers two API-based partnership tiers. The underlying External Partner API is identical for both; the difference is account visibility and branding isolation.

FeatureMerchant ResellerWhite-Label
Customer loginCan log in to Eskimo portalCannot log in to Eskimo — fully isolated to partner platform
BrandingEskimo brand visible to customerPartner brand only — Eskimo is not visible
Ideal forResellers who redirect customers to Eskimo's interfacePartners running their own storefront, app, or checkout flow
API accessFull External Partner APIFull External Partner API (same)
◈ White-Label is the recommended model for partners with their own checkout flow (e.g., own storefront with Stripe or another payment provider).

Section 2

Integration Flow

The standard end-to-end flow for White-Label and Merchant Reseller partners:

[1] Fetch available eSIM plans GET /all-data-plan (optional filters: coverageType, coverageCode, planType) ↓ [2] Customer selects a plan and pays on your storefront (Payment is handled entirely by your platform — Stripe, etc.) ↓ [3] Create a customer account [first purchase only] POST /users → returns accountId ↓ [4] Provision the eSIM — top up a data plan POST /esim/top-up → uses accountId + planId If the account has no eSIM yet, one is auto-activated and assigned. ↓ [5] Customer receives eSIM QR code + installation instructions via email (Delivered automatically by Eskimo after successful top-up. The QR code is NOT returned in the API response body.) ↓ [6] Customer installs eSIM — starts using data ↓ [7] Customer checks remaining data (via your dashboard) POST /esim/data-wallet → returns remaining data, expiry, status per plan
ℹ Eskimo credit is consumed at step 4. Ensure your partner credit balance is sufficient before provisioning. Monitor your balance via GET /partner-credit or the Partner Portal.
Section 3

Authentication

Every request must include three HTTP headers. Requests missing any header return 400 Bad Request; requests with an invalid signature return 401 Unauthorized.

HeaderRequiredDescription
AppIDRequiredYour unique partner identifier (from API Configuration)
TimestampRequiredCurrent Unix timestamp in seconds (e.g. 1749686400). Must be unique per request.
SignatureRequiredBase64( HMAC_SHA256( AppID + APIKey + Timestamp ) ) — using your API Secret Key as the HMAC secret

Signature validation rules:

  • The Timestamp must be within 5 minutes of server time
  • The same Timestamp value cannot be reused (replay-attack prevention)
  • The signature string concatenates: AppID + APISecretKey + Timestamp (no separators)
Python 
import hmac, hashlib, base64, time

app_id  = "YOUR_APP_ID"
api_key = "YOUR_API_KEY"

timestamp = str(int(time.time()))
message   = f"{app_id}{api_key}{timestamp}"

sig = hmac.new(
    api_key.encode('utf-8'),
    message.encode('utf-8'),
    hashlib.sha256
).digest()

headers = {
    "AppID":     app_id,
    "Timestamp": timestamp,
    "Signature": base64.b64encode(sig)
                        .decode('utf-8')
}
JavaScript (Node.js) 
const crypto = require('crypto');

const appId  = 'YOUR_APP_ID';
const apiKey = 'YOUR_API_KEY';

const timestamp = String(
  Math.floor(Date.now() / 1000)
);
const message = `${appId}${apiKey}${timestamp}`;

const signature = crypto
  .createHmac('sha256', apiKey)
  .update(message)
  .digest('base64');

const headers = {
  'AppID':     appId,
  'Timestamp': timestamp,
  'Signature': signature
};

Section 5

Data Plan APIs

5.1 Get All Data Plans
GET /api/external-api-adapter/all-data-plan

Returns the full catalog of available eSIM data plans. All filter parameters are optional query string parameters.

Optional query parameters (all optional):

ParameterTypeDescription
coverageTypeInteger0 = Global · 1 = Regional · 3 = Single Country
coverageCodeStringISO alpha-2 country or region code (e.g. SG, MY)
planTypeInteger1 = Fixed Plan · 2 = Unlimited Plan

Example: GET /all-data-plan?coverageType=3&coverageCode=SG&planType=1

Response fields per plan object:

FieldTypeDescription
planIdStringUnique plan identifier — use this as planId in top-up requests
planNameStringHuman-readable plan name (e.g. "Singapore 7-Day 5GB")
validityIntegerPlan validity in days
validityInfoStringHuman-readable validity label (e.g. "7 Days")
dataCapIntegerData cap amount. For Unlimited Plans this is the daily cap in GB (e.g. 3 = 3GB/day); for Fixed Plans, total GB for the plan
dataUnitStringUnit of data, e.g. "GB"
dataCapPerString"day" for unlimited plans; empty for fixed plans
pricesArrayPricing array with all supported currencies — USD, GBP, EUR, AUD, CAD. e.g. [{"USD": 18.0, "GBP": 14.5, "EUR": 16.9, "AUD": 27.0, "CAD": 24.5}]
priceInfoObject / nullExtended price info (currently null)
capacityInfoStringHuman-readable capacity description
additionalInfoStringAdditional notes about the plan
activationInfoStringActivation conditions (e.g. "Activated on first use")
canTopUpBooleanWhether this plan supports top-up after purchase
tetheringBooleanWhether hotspot / tethering is supported
phoneNumberBooleanWhether the plan includes a phone number
subscriptionBooleanWhether this is a subscription plan
subscriptionPeriodIntegerSubscription period in days (0 for non-subscription plans)
eKYCBooleanWhether the plan requires eKYC verification
promoEnabledBooleanWhether a promotional price is currently active
internetBreakoutsObject / nullInternet breakout configuration (currently null)
dataURLStringDeep link to the plan page on Eskimo (includes ?partner_id=PN… for affiliate tracking)
coveragesArrayList of covered countries/regions — see structure below
planFilterObjectCategory metadata — see structure below

coverages[] structure:

FieldTypeDescription
codeStringISO alpha-2 country code (e.g. "SG")
networks[].nameStringCarrier name (e.g. "Singtel")
networks[].types[]String[]Supported network types (e.g. ["4G", "5G"])

planFilter structure:

FieldValues
coverageType1 = Global · 2 = Regional · 3 = Single Country
coverageNamee.g. "Global", "Asia Pacific", "Singapore"
usageScheme1 = Fixed Plan · 2 = Unlimited Plan

8.1 Purchase (Generate) Voucher
POST /api/external-api-adapter/voucher/purchase

Generates a batch of vouchers for the partner. Uses the standard header authentication (Section 3) and is subject to the standard rate limit (Section 4).

Known request constraints:

ConstraintDetail
Max vouchers per request100. Requests above this limit return isSuccess: false, HTTP 400, message "Maximum 100 vouchers per request allowed."
startDate / endDateRemoved from the request — no longer accepted or required.

Confirmed response fields:

FieldDescription
batchIdTransaction ID for the generated batch
totalVouchersTotal number of vouchers included in the batch
totalPriceTotal credit charged for the batch

Success message: "Generate vouchers successfully."

8.2 Refund Voucher
POST /api/external-api-adapter/voucher/refund

Refunds a previously purchased voucher. Uses the standard header authentication — partnerid is no longer accepted as a request field; the partner is identified from the authenticated request headers instead.

8.3 Search Vouchers
POST /api/external-api-adapter/voucher/search

Searches vouchers issued to the partner. partnerid is no longer accepted as a request field (identified via headers). Supports lookup by batchID in addition to existing filters.

8.4 Generate Unique Gift Code

Generates unique gift codes in bulk for a partner campaign. Uses the standard header authentication (Section 3).
